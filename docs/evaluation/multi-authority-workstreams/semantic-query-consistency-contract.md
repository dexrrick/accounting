# Semantic query consistency contract

This note documents the shared semantic interpretation contract used by the V2 and legacy provider shapes. The V2 schema remains unchanged: consistency is checked against existing fields and is not encoded as a new provider field or cap.

`requiresUserSpecificFacts` is a model-produced observation. Deterministic validation checks that observation against operations and, when available, the user query; it never rewrites a contradictory raw value into a valid one. A proven contradiction rejects the interpretation as `CONTRADICTORY_FIELDS` in production and `CASE_FLAG_CONTRADICTION` in safe diagnostics.

The minimum specificity inference is tri-state. `true` means the query demonstrably applies a rule to a particular person, entity, transaction, or stated event. `false` means the phrasing demonstrably asks for a general rule, such as who qualifies, what conditions apply to a class, or an explanation of a rule. `undefined` means intent is ambiguous or the query cannot be matched safely to one issue. Unknown intent preserves the model flag; it is never treated as proof of a generic question. “Explain this to me” is an audience request, not claimant evidence by itself; direct first-person claim/status questions, named entities, and owned case facts can establish application.

`CALCULATE`, `DETERMINE_TREATMENT`, and `PREPARE_JOURNAL` always require case facts, including when these occur on individual issues under a mixed top-level `OTHER` operation. A false root flag is contradictory if any operation or query-aware issue proves case application. A true root flag conflicts with the query only if every issue is positively established as general. `EXPLAIN_RULE` is general by default, while explicit case-application wording can expose a conflicting false flag. `CHECK_ELIGIBILITY` distinguishes a general class or conditions question from an application for a specified person or entity.

Evidence requirements follow each issue's own specificity where it can be inferred safely. A single issue is checked against the whole query so qualification clauses do not become disconnected from the request. In a multi-issue query, a clause is assigned only when its subject match is unique and strong; otherwise the issue remains ambiguous. A known general issue gets `AUTHORITATIVE_SOURCE`; a known case-specific issue gets `AUTHORITATIVE_SOURCE_AND_CASE_FACTS`. For an ambiguous issue, reconciliation uses the model's root flag as a conservative fallback. This retains the current schema's top-level signal without imposing case facts on a separately identified general issue.

Diagnostics accept the query only as an in-memory consistency input. Safe output contains fixed reason codes, allowlisted field paths, and aggregate shape information; it must not contain query text, supplied facts, provider response text, keys, or URLs. The diagnostics describe interpretation consistency, not authority retrieval success or substantive answer correctness.
