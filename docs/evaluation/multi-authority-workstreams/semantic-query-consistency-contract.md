# Derived semantic specificity contract

The provider's current V2 wire object has exactly 12 top-level keys and omits `requiresUserSpecificFacts`. The validator also accepts the prior exact V2 shape with a boolean flag and the established legacy shapes for compatibility. When an older shape supplies the flag, it must still be a boolean, but its value is non-authoritative. The application derives the internal root flag and each issue's evidence requirement from the query and requested operations. A disagreement is reported as safe `CASE_FLAG_MISMATCH` telemetry, never as a semantic violation.

Specificity is inferred per requested issue. `CALCULATE`, `DETERMINE_TREATMENT`, and `PREPARE_JOURNAL` always require case facts, including issue-level operations under a mixed top-level `OTHER`. `CHECK_ELIGIBILITY` can be general when it asks who qualifies or what conditions apply to a class; it is case-specific for a stated claimant or transaction. `EXPLAIN_RULE`, `COMPARE`, `EXPLAIN_INTERACTION`, `FILING_REQUIREMENT`, and `OTHER` may be general or applied depending on the query. An audience request such as “explain this to me” does not identify a claimant. Direct claim/status questions, named entities, and owned case references can establish application.

The inference remains tri-state internally: proven application is true, proven general intent is false, and ambiguous wording is unknown. Unknown specificity conservatively requires case facts. Supplied-fact counts, the historical provider flag, and provider evidence hints do not establish whether the user asked for a case assessment. The root flag is the OR of issue-level specificity, with mandatory top-level operations as a lower bound. Evidence is derived independently for each issue; the root OR is never used as an issue fallback. This can conservatively require facts for an unmatched issue in a mixed query, while avoiding the opposite error of treating an ambiguous issue as general.

A single issue is checked against the whole query so qualification clauses remain part of the request. For multiple issues, clauses are assigned only when the issue subject has a unique, strong match. Ties or weak matches remain unknown and therefore use source-plus-case-facts evidence. Known general issues use `AUTHORITATIVE_SOURCE`; applied issues use `AUTHORITATIVE_SOURCE_AND_CASE_FACTS`; unsupported domains remain `UNRESOLVED` under the existing evidence contract.

Diagnostics accept the query only as an in-memory derivation input. Their safe output contains fixed reason codes, allowlisted paths, aggregate shape information, `caseFlagMismatch`, and `nonViolationCodes`; it must not contain query text, supplied facts, provider response text, keys, or URLs. The diagnostics describe interpretation and routing metadata, not authority retrieval success or substantive answer correctness.
